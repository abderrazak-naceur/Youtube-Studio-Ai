# v0.19 Authentication & Tenant Isolation

## Purpose

Enforce authentication and multi-tenant isolation (DATA-MODEL §6, SECURITY-COMPLIANCE §1, PRODUCT-REQUIREMENTS tenant isolation). Callers must authenticate, and every tenant-scoped request is checked against workspace membership and role.

## Identity model

- `User` (email + salted PBKDF2 password hash) and `Membership` (user ↔ workspace + `WorkspaceRole`: Editor < Reviewer < Owner).
- `POST /api/v1/auth/register` and `/login` issue short-lived JWT access tokens. Self-issued for the MVP; swappable for OIDC behind the same contract (AUTHENTICATION.md).
- Provider/signing secrets live outside source (env `Jwt__SigningKey`); a development/testing fallback keeps local runs and CI working.

## Enforcement

`IWorkspaceAccess` resolves the authenticated user from the principal and checks membership/role. Applied via `[Authorize]` plus explicit checks:

- **Workspaces**: list/get/create are scoped to the caller's memberships; creating a workspace makes the caller its `Owner`.
- **Video projects**: list/create/get/script/scene-plan/start require membership on the project's workspace; non-members get `404` (no existence leak).
- **Approval**: approve/reject require at least the `Reviewer` role; lower roles get `403`.
- **Artifacts, costs, content genome, audit**: require workspace membership.

## Verification

Backend coverage: register/login (success, duplicate, wrong password, short password), password hashing, workspace-access role checks, Editor forbidden from approving, and all tenant-scoped controller tests run with an authenticated principal. CI e2e now registers a user, asserts anonymous access returns `401`, and drives the whole loop with a Bearer token.
